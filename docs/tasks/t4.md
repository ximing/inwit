# T4: 捕捉 inbox + 线程 + 任务队列 worker

工作目录 /Users/ximing/project/mygithub/inwit。读 docs/prd.md §2.1、§2.5、§5。

## 目标
1. **捕捉 API**（全部挂认证）：
   - POST /api/captures {content, threadId?} → 写 captures(type=text,status=pending) + 写一条 jobs(type=digest, payload={captureId}) → 立即返回 capture（异步消化，不等结果）
   - GET /api/captures?threadId=&status= 列表（倒序分页）
   - GET /api/captures/:id 详情（含消化出的卡片）
   - DELETE /api/captures/:id（级联处理其卡片：删卡或保留需说明选择）
2. **线程 API**：
   - GET/POST /api/threads，GET/PATCH/DELETE /api/threads/:id（PATCH 支持 title/goal/status）
   - POST /api/threads/:id/archive
3. **任务队列 worker**（参考 vital apps/server/src/worker.ts + src/agent/jobs.ts 的模式，用 PG 表做队列，不引 redis）：
   - src/worker.ts 独立进程：`pnpm --filter @inwit/server worker` 启动
   - 轮询 jobs 表取 status=pending 且 run_at<=now 的任务，UPDATE ... SET status='running' WHERE id=... AND status='pending' 防并发（或 FOR UPDATE SKIP LOCKED）
   - 失败重试：attempts 上限 3，指数退避，最终 failed 记 last_error
   - 本任务 digest/evolve 处理器先留 stub（写日志、把 job 标 done、把 capture 保持 pending），T5 实现真正消化；但队列机制必须完整可用
4. **任务看板 API**：GET /api/jobs?status=&type=（分页）、POST /api/jobs/:id/retry、POST /api/jobs/:id/cancel

## 验收
- 起 server + worker，curl 注册登录后 POST /api/captures 两条内容 → GET /api/jobs 能看到 digest job 被 worker 消费为 done（stub 处理器）
- GET /api/captures 返回列表
- 建线程 → 带 threadId 捕捉 → 按 threadId 过滤正确
- 手动把某 job 改 failed，调 retry 后重新入队被消费
- `pnpm -r typecheck && pnpm -r build` 全绿
