## 背景

**P1（来自 T28 验收）**：capture 提交后自动打开新文档 → editor sync 激活 → `syncPolling()` 在 `syncActive()` 时直接 `stopPolling()` → digest job 完成后，界面上的「消化中…」不会翻转，直到刷新或离开文档视图。T28 给「消化中」做了 AI 皮肤与完成回落（卡数淡入），这个收束时刻在主流程里永远不 live 出现，被用户明确感知。这是既有的「sync 期间停轮询」架构，T28 只是把它放大——本任务从根上修。

**P4（来自 T28 验收顺带发现）**：worker 日志里 weekly_report job 持续失败（`weekly report document missing card links`，3 次重试耗尽）。与 T28 无关，先排查根因再定修复。

## 目标 1：sync 激活期间的轻量轮询（web）

原则：**保护编辑器不被轮询数据clobber是 `syncPolling()` 停轮询的初衷，这个保护不能破**；但「状态字段」（status / cardCount / proposedCount / failReason / job 进度）与正文内容（contentJson/preview）是两类数据，前者在 sync 激活时刷新是安全的。

- `syncPolling()` 不再在 `syncActive()` 时一刀切 stop：sync 激活时进入**轻量轮询模式**——只当存在 pending 文档（列表或当前打开的 `this.doc`）或上传中时启动，tick 里只刷新状态类字段：
  - 列表 pending 项与当前打开的 pending 文档：拉详情（复用 `fetchMergedItem` 或新增只取状态字段的 API 调用），合并时**只写 status/cardCount/proposedCount/failReason/updatedAt 等元字段，绝不覆盖 contentJson/preview/编辑器相关状态**。
  - `this.doc` 是当前打开文档时同样只合元字段；`jobs` 列表刷新（`refreshJobs`）照走现有逻辑。
- sync 未激活时行为完全不变（现有 tickPending 全量合并）。
- 纯逻辑（哪些字段可合并、何时启动轻量轮询）抽到 `lib/doc-list.ts` 或新的 `*-logic.ts`，配 vitest 单测（参考现有 lib 下测试风格）；merge 逻辑重点测：sync 激活 + 文档 digested → 元字段更新、contentJson 原样保留。
- 完成回落联动：状态 live 翻转后，T28 的 `.card-count` 淡入与竖边消失应在用户**留在文档视图**时也发生（DocStreamRow 的 `useJustDigested` 已按 props 变化工作，确认即可）。
- 轮询频率沿用 `POLL_MS`，不为轻量模式新造间隔；页面不可见时的既有节流逻辑（如有）不动。

## 目标 2：P4 weekly_report 失败排查与修复
